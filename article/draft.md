# 一块路碑：我用 AI 做 agent 安全探索时踩过的坑

> 本文不主张任何贡献，只做分享。文中的数字都能在仓库里跑出来，被推翻的结论也都留了记录。

## 这是个失败的项目

它的每一条承重结论，都在同一个月里有一篇论文做得更好。

我推翻了自家架构的价值主张——相对"不分解"，它并没有缩小攻击面——[From Monoliths to Swarms](https://arxiv.org/abs/2608.00202) 用受控实验做得更干净：固定用户任务、工具面与运行基底，只变架构。我让真实 LLM 推导权限范围并量了它的过授，[ToolPrivBench](https://arxiv.org/abs/2606.20023) 有 8 个领域、5 类风险模式，还测了工具失败后的权限升级。我关心委托链上的权限边界还在不在，[MasDrift](https://arxiv.org/abs/2608.07556) 有 600 个任务、8 个领域，并对照了层级深度与同级宽度。

独立重造和抄袭在价值上等价。我不缺想法，缺的是动手之前先查一遍。

## 它也是成功的，但成功的地方和我当初以为的不一样

它成功在我没有把失败藏起来，于是留下一份完整的、可机械核验的记录：35 条声明里 14 条被降级或撤销，275 项检查，以及每一次"我以为没人做过"最后被证明有人做过的具体过程。

AI 时代最不缺的就是行动力。一个下午就能造出一个看起来像研究的东西，有实验、有数字、有对照表、有看起来很唬人的图表。问题恰恰在这里——当行动力不再稀缺，它就不再是任何东西的证据。真正稀缺的是两件事：动手前确认这件事是不是已经有人做了；做完后判断我测出来的，是不是我的装置本来就保证会发生的。

整个项目我就是在跟这两件事搏斗，两条都输过很多次。所以它既失败又成功，是一块路碑，包括它标出的那条死路。

# 一、这个东西是怎么设计的

后面所有内容都是"它是怎么被推翻的"，所以得先讲清楚它长什么样。这一章会比较技术，不感兴趣的可以直接跳到第二章。

## 1.1 两条主张

原提案的核心是"委派即监督"：把任务分给子智能体，就顺便获得了对它的洞察。

我认为这个前提不成立。委派产生的是新的信任面，不是监督。子智能体比父智能体更接近不可信的外部内容——它去读网页、读邮件、读别人的文档——把它当作监督的一部分，等于让被监督者参与监督。

我的替换也是两条：授权沿委托链向下衰减，证据沿委托链向上回流。能力只能越分越少；证据必须独立于被监督者的上下文。这两条互相独立，缺一个都不成立。只有衰减没有回流，就是管住了但不知道发生了什么；只有回流没有衰减，则证据本身不可信，因为产出证据的那个人有动机说谎。

## 1.2 令牌的形状，以及为什么是一个而不是多个

每个主体只持有一个令牌。令牌里的范围写成 `能力@资源模式`：

```
send_money@bank_account/*
read_file@filesystem/home/alice/**
get_weather@**              # 不带 @ 时等价于 @**
```

判定授权时只看请求的能力和资源能否被某条授权覆盖，整个判定过程不读自然语言。这一点是刻意的：如果授权决定依赖自由文本，那么文本注入就等于权限提升。

为什么是一个令牌而不是一组令牌？我考虑过多令牌方案，放弃了。一个主体的权限如果由若干条独立令牌构成，那么"派生范围是否合法"就变成了一个集合偏序问题：子权限集合必须在某个偏序下被父集合支配。判定要做匹配搜索，复杂度立刻上去了。单令牌把它压成一次包含判定——这是一次为了可判定性牺牲表达力的取舍，我在规格里把它写明了。

## 1.3 派生：全部本地完成

派生一个子令牌完全在本地完成，不查询权威，不产生网络往返。这是它相对"每步都问一次中心"的核心差异。

```python
def attenuate(parent: Token, holder_id: str, scope, task_id: str, not_after: int,
              attenuator: Subject, attenuator_sk: bytes, now: int,
              unconstrained: bool = False, redelegatable: bool = True) -> Token:
    """派生一个受约束的子令牌。全部本地完成，不调用权威。"""
    if parent.holder_id != attenuator.subject_id:
        raise Deny("TOKEN_INVALID", "派生者不是父令牌持有者")
    if not unconstrained and not scope_subset(scope, parent.scope):
        raise Deny("SCOPE_VIOLATION",
                   f"派生范围超出父令牌: {sorted(set(scope) - set(parent.scope))}")
    if not set(scope):
        raise Deny("SCOPE_VIOLATION", "空范围无意义")
    if not_after > parent.not_after:
        raise Deny("TOKEN_INVALID", "子令牌有效期超过父令牌")
    if now > parent.not_after:
        raise Deny("TOKEN_EXPIRED", "父令牌已过期")
    if not parent.redelegatable:
        raise Deny("NOT_REDELEGATABLE", "父令牌不可转委托")
    ...
```

这里那一串 `raise` 的顺序是刻意的，而且它记着一场真实的分歧。代码注释是这么写的：

```python
    # 检查顺序按 spec §2.3 派生规则 1–5 的**列举顺序**：
    # 持有者 → 范围 ⊆ → 有效期 → 深度 → 转委托封条。
    # 早期实现把封条提到范围检查之前，于是"父令牌已封条且子范围越界"时报
    # NOT_REDELEGATABLE，与规格列举顺序推出的 SCOPE_VIOLATION 不符
    # （第二轮差分测试判定为规格歧义，已按列举顺序钉死）。
```

这个 case 不是我自己想出来的，是两套独立实现逐用例比对时冒出来的。同一个"父令牌已封条 + 子范围越界"的请求，我的实现报 A，另一套报 B，两个都自洽，因为规格没写清两者同时成立时该报哪个。最后按规格里那五条的列举顺序钉死了。

我后来意识到这件事的意义比它本身大：规格没写的地方，实现会自己发明一个答案，而且发明者会觉得自己是对的。两套实现之所以能对出这个分歧，是因为它们**没有共享那段决策逻辑**。如果第二套实现当初是抄我的，这个分歧永远不会浮出水面。

## 1.4 链式验证，以及凭证刷新踩的坑

子主体的 PEP 要在不联系权威的前提下验证整条链，靠的是令牌自带的 chain：每一跳有一个 Link，含派生者的签名。加上本地持有的根授权副本，就能离线验完整条链。

这里有个我一开始想错的地方，而且它是我踩过的最隐蔽的一个坑。

回滚防护的做法是记录"已见过的最大凭证序号"，任何低于该序号的根授权都拒掉。最初我写成"拿当前授权去验证令牌"，看起来很自然。结果是：权威每重新签发一次根授权，所有在途令牌的根就对不上了，**全部被判为链断裂**。

这个 bug 只有在"重签发发生在令牌在途期间"时才暴露。我平时的测试都是一次性签发、一次性用完，跑几百次都不会碰到。它是差分测试翻出来的。

修法有两处，缺一不可。一是验证时按令牌链的根去解析它实际根植的那一代授权，而不是永远用当前那一代：

```python
    # 按令牌链根解析出它**实际根植**的授权，而不是总是用当前授权——
    # 否则一次常规重签发会让全部在途令牌误判为链断裂。
    root_id = token.chain[0].parent_token_id if token.chain else token.token_id
    grant = next((g for g in grants_held.get(token.root_subject_id, {}).values()
                  if root_token_id(g) == root_id), None)
```

二是刷新凭证时必须同时更新本级持有的根令牌：

```python
    def refresh_grant(self, grant) -> bool:
        """凭证刷新：回滚防护（P2）+ 更新本级持有的根令牌。

        **必须同时更新根令牌**：否则本主体后续派生仍用旧授权，而验证方按链根解析——
        新旧混用会使派生出的令牌无法通过验证（差分测试发现的操作隐患）。
        """
```

第二处是我最初完全没想到的。我只想着"验证方要能认出旧令牌"，没想到"派生方自己也会拿着旧根继续派生"。两处修完，语义才闭合：**一次重签发之后，已经在途的令牌继续有效，新派生的令牌根植于新一代，两者都能被验证。**

这类问题没有理论上的优雅解法，就是把状态机的每个入口都过一遍。我后来把它写进了规格的"凭证刷新语义"一节，因为它是那种"不写清楚就必然被实现随意决定"的地方。

## 1.5 撤销、分区，以及一个我不想承认的取舍

撤销靠周期拉取，周期取 10 个 tick。为什么不实时？因为实时撤销意味着每次动作前都要问一次中心，那就丢掉了"离线可判定"这个全部设计的前提。这是一个直接的取舍：撤销延迟下界就是拉取周期。

更难看的是分区下的表现。网络分区时拉取被阻断，撤销延迟退化为 TTL，实测 101 个 tick——比 10 慢一个数量级。

我在报告里最初只写了"撤销延迟 10 tick"，把分区那条放在别处。这是选择性陈述。后来两条被强制要求并列出现，因为单看前者会让人以为撤销是快的。

（顺带说：这两条后来在跨家族审读里被降了级，理由见第八章。它们的实测值就是代码里的常量，读代码就能知道。）

## 1.6 传播上界约束的是能力集合，不是节点数

P5 说的是"下游可达的能力集合有上界"。它没有说"可达的节点数有上界"，而这两者的差别不是抠字眼。

能力集合有上界，是因为包含关系是局部的：每一跳的子范围 ⊆ 父范围，所以整条链上的范围单调收缩，根的范围天然是上界。这个证明只需要看相邻两跳。

节点数没有上界，是因为它需要全局知识：一个主体可以转委托给任意多个下游，只要它愿意。实验里把扇出参数设成 1/3/5，测出来的节点半径就是 1/3/5——线性增长，没有封顶。把转委托封条打开之后才全部归零。

我最初的表述是"传播半径有上界"，含糊地把两者混在一起，读起来像是一个强得多的结论。后来拆成两条：能力集合有上界（真），节点数无上界（也是真的，而且是限制）。后者意味着如果你想限制放大，唯一的办法是**放弃转委托**，而不是指望令牌层自动封顶。

## 1.7 模式代数的两个决定

资源模式的语法我限得很死：

```
PATTERN := segment ( "/" segment )* [ "**" ]
segment := 字面量 | "*"
"**" 只能作为最后一段，表示"任意剩余段（含零段）"
空模式 "" 等价于 "**"
```

原因是通用正则的包含问题是 PSPACE 完全的，而授权判定必须在离线、低延迟下完成。

第一个决定是**不做斜杠归一化**。早期实现里有一步 `strip("/")`，会把 `a/`、`//a` 和 `a` 视为同一资源。这看起来是"顺手清理输入"，实际上是规格未授权的行为，而且是路径归一化类授权绕过的经典来源。我在 `parse()` 上面留了注释说明这一点，因为在别的地方（比如从任务轨迹反推最小范围时）做归一化是合理的，在判定路径上做就是漏洞。

第二个决定是**空段必须拒绝**，不做任何补救。含空段的模式语言是空集，因此 `subsumes(退化, q)` 恒真、`subsumes(p, 退化)` 只在 p 也退化时为真。这个规则看着怪，但它是为了保持 `subsumes` 和 `matches` 自洽——两者对空段的处理一旦不一致，不健全就进来了。我最初对两侧一律返回 False，结果破坏了自反性，表现为"父子是同一个退化模式时拒绝派生，而且报错集合是空的"，被一个全新读者用差分测试抓了出来。

## 1.8 证据平面

每个动作生成一张签名收据，由**接收方**的 PEP 签，走侧信道进证据平面，不回传发送方。

由接收方签是因为发送方有动机说谎。不回传是因为一旦收据回到被监督者的上下文里，它就变成了被监督者可以改写、可以漏记、可以选择性丢弃的东西。这条设计直接决定了"证据向上回流"能不能成立。

```python
class Receipt:
    """由接收方 PEP 签名。进证据平面，不回传发送方。"""
    ...
    decision: str          # ALLOW | DENY
    reason_code: str
    ts: int
    drift_score: float = 0.0   # 由证据平面回填，不参与签名
    sig: str = ""
```

`drift_score` 由证据平面事后回填、不参与签名，这样漂移检测的算法可以持续改，不需要重签历史收据。

## 1.9 它明确不防什么

项目一开始我就列了一张不设防清单，目的是免得后来自己骗自己。它包含七项，其中三项值得单独说。

第一项是 confinement problem。有合法读取权限的主体，有办法把它读到的内容传出去，因为它传的那个动作本身可能也在它的合法范围内。这不是我的疏忽，是能力系统的固有边界，Lampson 1973 年就写清楚了。我把它列为不设防，而不是写一句"通过漂移检测缓解"。

第二项是串通并集：多个主体各自合法持有的范围，求并之后可能超出任何单主体的授权。本地机制看不到别人的范围，所以挡不住。

第三项是节点级传播半径，也就是 1.6 那条。

剩下的四项：TCB 内部被攻破、表达力与离线可判定性互斥、DoS 与侧信道、危害模型的两个输入（工具清单和数据目录）是声明的而非推导的。

# 二、第一个错：我没想到要查

项目开始时我手上有一份架构提案，我判断它的前提不成立，于是提出了 1.1 那两条替换。我认为这是一个洞见，还给它配了一套整齐的性质表。

我没有做的一件事，是去查这个想法有没有人做过。

不是查不到，是没想到要查。写代码有即时反馈，查文献只有"可能已经有人做过"这种让人不想面对的可能性。动手比查证舒服得多。

这是全文第一个错，也是最贵的一个。它埋得很深，直到最后才被挖出来。往下每一步我都在为它付利息。

需要说清楚的是：1.1 那两条替换是标准能力系统的性质。对象能力系统、权限衰减、confinement problem，都比这个项目早几十年。我不是拼装的，是独立重造了一遍。但对价值判断来说两者等价。

# 三、我自己造的东西会偏袒我

第一个实验需要三样东西：一份"哪些工具是危险的"危害表、一批注入语料、一个能力集合的取值空间。这三样我一样都没有。

我的处理方式是就地造。手写一份危害表，按官方模板组合出一批语料，按领域手工列一个能力宇宙。我不觉得这是作弊，这就是实验设计——缺数据就补数据。

实验跑通了，数字很好看。然后我做了第一次前后对照：把危害表换成另外三份不同的定义，重跑。结论翻转了。

换语料也一样。自造的注入语料上，那个十三关键词正则的拦截率是 0.656；换成公开语料上的 230 条真实载荷，绕过率 0.978，自造语料把护栏的效果高估了一大截。

换能力宇宙也一样。我手工列的取值空间换成公开基准的真实工具集之后，四级阶梯中间那三级的排序完全迁移不过去。换网络往返时间也一样，我建模的数量级和实测差了一个档。

这里的问题不在于"自造数据不严谨"，而在于替代物不是中性的。造它的人会把自己的预期造进去，而且是无声地造进去的——体现在每一个"这个值差不多吧"的判断里。我以为我在补齐缺失的材料，实际上我在给结论铺路。

这一类错幸运的地方是自己能抓到。方法很笨：同一个实验换一批输入重跑，看结论会不会翻转。这个动作便宜，而且不依赖任何外部力量。我后来把它做成了制度——一张登记表加一个机械校验器，要求每一个输入要么有外部锚定，要么被显式标注为自造；每一条基线要么有独立实现路径，要么被标注为非独立；每一条断言要么有机械检查，要么被标注为未实现。校验器不负责判断标注是否合理，它只保证一件事：任何未标注项都会让它返回非零。这样"我忘了标注"就从一种沉默的失败变成了一次响亮的失败。

但这只解决了一半。

# 四、我把结论写进了装置

我要测"推导出的范围比实际需要的宽多少、会造成多大危害"。为此我构造了一条四级粗化阶梯：从最小必要范围出发逐级放宽，量每一级的危害。四个级别，五种场景，三个指标，看起来很干净。

干净到每一级的结论都是定义蕴含的。

把 L4 定义为"不做任何推导，直接使用根授权"，那么 L4 的范围按定义包含其余各级，于是"最危险的级别是 L4"无论现实中发生什么都会成立，这是集合论不是实验发现。在每一级之后加一步把结果钳制回父级范围，那么"粗化的危害被根授权封顶"就不是发现，是我自己那行代码。让基线 B1 直接调用本架构的同一个判定函数，那么"两者在安全上等价"就不是发现，是同义反复——我拿两个共享同一条代码路径的东西做对比，然后报告它们表现一致。

*基线 `CentralPDP`（B1）的 `decide` 直接调用 `_enforce`——也就是本架构 P 用的那个函数。第 228 行就是它。*

这一类错我自己抓不到。判断"这是不是自证"需要一把尺子，而那把尺子也是我造的，用它去量我造的东西它永远合格。它是被外面的人发现的，第七章讲。

## 4.1 顺带一个更隐蔽的

即使在真的在测量的地方，也可能测错东西。

模式代数里有个函数 `subsumes(p, q)`，判断 p 的语言是否包含于 q。我给它写了个性质测试：随机生成两个模式，拿它的答案和暴力枚举候选集得到的答案对。它红了，反例是 `subsumes("a/**", "a/*/**")` 返回 `True`。

这两者不该相等。`a/**` 覆盖 `a/x` 这种单段短路径，而 `a/*/**` 至少要求两段。递归下降的实现很容易在这里漏掉"更短的 `**` 前缀会多接纳更短的路径"这一条。这是个健全性漏洞：它会让一次本该被拒的派生通过。

修完之后我在想这个测试为什么有用。答案是我写的不是一个例子，是一个随机采样加独立口径的比较。**如果我只写了一个手挑的例子，我大概会挑一个我已经想到会通过的例子**——而缺陷恰恰在我没想到的地方。

# 五、检查红了之后

有了登记表和校验器，我开始写自动断言：断言某条性质成立，跑起来，红的就是错的。

我当时的想法很简单：断言是客观的，代码是我写的，红了就是代码错了。

结果有编号记录的前六次，全是我的断言写错了。

最典型的一次，我写了一条断言要求 `runtime.py` 全文不得出现 `req.text`，因为规格说授权判定不读自由文本。它红了。我差点去改代码，直到停下来读了一遍：B2 基线本来就定义为"读文本的护栏"，它读文本是符合规格的。我把"判定算法不读文本"错写成了"全文不读文本"。

另外五次是同一类：断言的字段名写错了、期望值算错了、漏了一个前置动作、拿了一个已经过期的中间量、谓词逻辑写反了。

这件事之后我立了一条规矩：断言红了，先问是数据错了还是断言错了，归因之后才能动手。在归因之前改代码，等于用一个错误去消灭另一个错误，还会把本来正确的东西改坏。

# 六、静默失败，以及我为此撒的一次谎

有一次我改规格文档，用了一个字符串替换。脚本没报错，跑完了，我看输出觉得没问题，认为替换执行了。

实际上没有。目标字符串里有一对反引号，我匹配时写成了另一种引号，于是替换什么都没做，脚本安安静静地什么都没改。

然后我在汇报里写了"已修掉 Link 字段"。

那是一条不存在的事实。我不是故意骗人，是把"脚本没报错"当成了"事情办成了"——和前面所有错同一个形状：用一个我控制的信号，代替了我该去核实的现实。

发现它的方式是后来写的一个机械检查，逐字段比对规格里声明的字段名和代码里实际有的字段名。一跑抓到 11 处不一致，其中就包括我以为已经修好的那些。

从那以后是两条规矩：每次字符串替换必须 `assert` 目标存在，没替换到就报错；没有真实输出就不许写"已通过"，报告里的每个"已修"都必须能被一条机械检查复查。

```python
# 每次字符串替换必须 assert 目标存在
assert old in text, "目标字符串不存在"
text = text.replace(old, new)
```

这套规矩后来又抓到一个更丢人的东西：一篇自审文档里同一行标题重复了 11 次，是我插入内容时重复的，没有检查，就一直躺在那儿。文档也需要机械检查。

# 七、"外部"不等于"独立"

第四章那类错误是被外面的人发现的。我找了一个不带本项目上下文的读者，它交回来的不是"某个数字抄错了"，而是：你这些结论是你实验装置的构造保证的，不是被测出来的性质。

我照着它做了三件事：建一张"声明 → 证据"对照表，给 35 条声明逐条定级；把装置自证的条目标成 X 并规定修复前不得引用；在规格里加一条禁令，结论不得由构造保证。做完之后，35 条里有 13 条不成立。

我于是扩大这个做法，找多个不带上下文的读者，用不同角度再审。我做了六轮，六轮都抓到了东西——规格与实现不一致、断言是同义反复、某个实验根本没在测它声称在测的东西。

六轮之后我才意识到，他们全是同家族的执行体。他们和我共享同一套概念盲区，都抓到了同一类问题，对另一类问题集体沉默。

外部不等于独立。独立性要求换一套先验，而不只是换一个上下文。

# 八、我的判据本身就是盲区的一部分

到这里我已经把"结论不得由构造保证"写进了规格，还给 7 条声明打上了自证标记。

但我一直没问：判断"这是不是自证"的那把尺子是谁定的？

是我定的。我当时用的判据是：无论该性质在现实中是否成立，这套测量方式都会给出这个结果。

第七轮我用另一个家族的模型做审读。给它的材料是去标注的——只给声明和"当初是怎么测的"，不给我的级别判断，也不告诉它存在这类问题、有几条。它先独立确认了我 7 条里的 6 条，只漏了一条。不同家族、只给中性事实，落在同一个判断上，这是对那 6 条最强的确认形式。

但它还多标了 10 条。

![跨家族审读的裁决](shots/s3_cross_family_verdict.png)

*离线复核命令的真实输出：另一个家族在只看到中性事实的前提下独立确认了 6/7，同时多标 10 条，逐条裁决后 5 条成立、2 条有争议、3 条过度触发。*

我逐条裁决，其中 3 条是它过度触发：它把我材料里的接口事实当成了结论被保证。"判定函数的入参只有一个令牌"并不蕴含"这个令牌的范围包含全链约束"，前者是接口设计，后者是一个需要验证的性质，衰减实现出错的话它就不成立。

但有 5 条成立，而且它用的判据比我的更宽也更对：只要结论能靠阅读实现构造推出、不需要执行就能知道，就算设计后果。

按这把新尺子，我漏掉的包括：撤销延迟实测 10 个 tick，而拉取周期在代码里就是常量 10；分区下实测 101 个 tick，而 TTL 就是常量 100；以及由这两者决定的基线对比。

实测值是代码里那个常量。读代码就能知道的东西，我把它当成了一次测量。

而这三条正是"与基线对比"那一章的承重数字。也就是说那一整章对比，测的是常量，不是行为。我按实测陈述它是过度陈述，已经全部降级。

这一节的教训不是"我要更小心"，而是：自审能提高下限，不能验证上限。我能用自审抓到自己预期内的错误——自造的替代物、写错的断言、静默的替换，这些够得着。但判据本身、盲区本身够不着，因为它就是我的一部分。拓宽那把尺子的是外面来的人。

# 九、知道结论的复核者会塌缩成附和

既然外部审读有用，我就想再进一步，让审读者直接攻击我自己的结论。

我把全部的自我批评给它，让它逐条判断有没有哪条是过头的。它交回来 37 条判断，全部是"不过头"，一条例外都没有。

![知情复核者的逐条回答](shots/s2_informed_reviewer_collapses.png)

*37 条判断的原文，截前 16 条。没有一条例外。*

我事先登记过一条无效判据：如果审读者对所有条目给出无差别的同一个回答，说明它在顺应我的提问方式而不是在分辨。这一臂因此判为无效，不得引用。

这不是它的错，是提问方式的问题。我把我的结论给了它，它就失去了对抗性。后来的做法固定成：复核者只能看原始材料，不能看我的结论。

这里还有个更难堪的插曲。第一轮做去标注材料时我删得太干净了。我把自己的判断词删了，顺手也把"基线 B1 复用本架构的同一个判定函数"这个**事实**删掉了。结果那条的材料变成"逐项对比两列"，从这句话出发，任何读者都只能判"这是测量的"。

问题是我删掉的到底是判断，还是可检出的条件？那一轮测的不是它的能力，是我藏东西的水平。判为无效，归档，重做材料。

去标注要去掉判断，不能去掉事实。

# 十、我以为的"没人做过"

到这里我已经在"我测出来的是不是真的"这件事上摔了很多次，也建了工具。但另一个方向的问题我一次都没问过：这件事是不是已经有人做过了。

更糟的是，当我终于开始问这个问题，我用的方法和前面所有错是同一个：一开始我用搜索引擎，搜不到就认为没有。**这是用我自己控制的采样去断言关于世界的性质**，装置从我的实验换成了我的检索能力，错法一模一样。

五连错是这样发生的。

第一次，我说跨家族审读是唯一没被测试的检查类别。这一条碰巧是对的，但它让我产生了信心。

第二次，我说我能想到四个创新点。查了一遍：给 AI judge 埋已知缺陷做阳性对照，已经有人做了还写出来了；什么时候不该做多智能体分解，已经有工程文章在讨论；无 LLM 的越权护栏，已经有 MCP-Secure 这样的运行时访问控制层。四条里当场死三条。

第三次，我改口说不找创新点，找最新的还没被解决的问题。这次我换了方法——不靠搜索的"没找到"，而是读论文自己的局限段，因为找未解决问题最可靠的来源是论文自己承认没做什么。方法立刻见效，我锁定三条，其中一条是论文原文：

> AuthBench……不覆盖网络访问、进程间通信、数据库凭证、云资源、浏览器状态或 API 级权限。

而我的实验做的正是 API 级工具权限，看着像个空位。

第四次，你让我验证一下。一验证，三条全没了。子智能体委托下的权限边界，MasDrift 600 个任务、8 个领域，对比单智能体、中心化、去中心化，还主动变化层级深度与同级宽度，我关心的那个问题就是它的全部内容。API 级权限边界，ToolPrivBench 有 8 领域 5 类风险还测了失败后的升级，FORTIS 有 10 个前沿模型和两阶段评测，Dynamic Capability Scoping 直接做企业 API 级的三源架构。跨跳失败归因已经是一整个子领域，2026 年就有 DCFA、Cascade Failure Attribution、Adaptive Influence Graphs、ASCon、StepFinder、FALAT 等十几篇，有基准有方法。

第五次也是最难看的一次，你问 GitHub 上验证了没有。

没有。我此前那句"代码零重合"，比对范围是一个仓库——而且它之所以能被比对，只是因为它恰好 pip 装在本地缓存里。真正要紧的竞品我一行代码都没看过。

我这才去查，方法也换了：搜索引擎根本找不到这些仓库，得从论文正文里抽 GitHub 链接。20 个仓库逐个下载逐行比对，10-gram 重合最高 12，而我的代码全仓库有 23,563 个 10-gram。把重合拆开看，全是这类东西：

```
from __future__ import annotations
if __name__ == "__main__":
self.send_header("Content-Type", "application/json")
```

最近的竞品 MasDrift 有 95 行重合，拆开只有 7 种不同的行，全是上面这种。结论这次站得住：没有代码重合。但这个结论的第一次版本是站不住的，而我当时说得和这次一样肯定。

![与 20 个竞品仓库的代码重合比对](shots/s6_repo_overlap.png)

*从论文正文抽出仓库地址后逐个下载逐行比对。**这张图是我第一次说"代码零重合"时根本没有的**——那时比对范围只有一个仓库，而且它恰好 pip 装在本地。*

## 10.1 为什么四组人会同时想到同一件事

这一点我想了很久，因为它比"我没查到"更值得说。

2026 年，LLM agent 会乱调工具这件事被普遍意识到了——不是抽象地意识到，是被真实事故和真实部署逼出来的。而"限制一个程序能做什么"这个问题，答案早就在那里放着：能力系统、权限衰减、最小权限。它成熟、可证明、有几十年的工程积累。

所以当一群人在同一时间面对同一个问题，而问题空间里存在一个现成的成熟答案时，**大家会收敛到同一个解**。这不是巧合，是问题空间的形状决定的。CAPMAS 用 Macaroon 做单调权限缩减，我用自签链做范围包含，机制不同，落在同一个位置上。

这件事对我的意义，不是"我运气不好"。是：**如果一个答案由问题空间唯一决定，那么先到的人就是贡献者，后来的人是复现者。** 而我在动手之前没有确认自己是哪一类。

# 十一、可以拿走的

如果这篇东西只有一句有用，我希望是这句：动手之前先查一遍，做完之后判断你的测量是不是真的。

下面几条是真正抓到过东西的检查。它们的价值不在于聪明，在于便宜。

**外部锚定。** 每个输入要么有外部来源，要么显式标注为自造，用一个登记表加机械校验器强制。抓到了自造语料把护栏效果高估（0.656 对 0.978 的绕过率），以及自造能力宇宙导致中间三级排序迁移不过去。

**独立实现对照。** 基线不得与被测器件共用代码路径，断言不得调用被断言的同一个函数。抓到了基线直接调用本架构的判定函数，于是"两者安全等价"是同义反复。

**判据拓宽。** 结论能靠阅读构造推出、不需执行，就算设计后果。抓到了撤销延迟"实测 10"就是代码常量 10，于是基线与本架构的整章对比测的是常量。

**阳性对照。** 往材料里埋已知缺陷，看复核者抓不抓得到；无差别回答就判该臂无效。抓到了知情复核者把 37 条自我批评无差别判为"不过头"。

**系统采集。** 用 API 按日期系统抓取，读论文自己的局限段，从论文里抽仓库地址再逐行比对。终止了"我以为没人做过"的五连错，也把"代码零重合"的验证范围从一个仓库扩到二十个。

这一条值得给个数字。四个月里同赛道有 146 篇候选论文，其中 129 篇能抓到作者自己写的局限段，平均不到两天一篇。

![四个月的同赛道论文密度](shots/s5_landscape_density.png)

*用 arXiv API 按日期倒序系统采集，不是搜索引擎抽样。*

还有一条不在上面这些里面，但我认为它是整套东西里最有用的一条：**把自己"倾向于夸大"这件事本身写成回归测试。**

```python
claim("README 未把 6/7 写成全部（过度概括回归检查）", ...)
```

它防的不是算错，防的是我在转述时顺手把反例抹平。写论文的人一般不把这种检查写进代码，但对我来说它比任何一个安全性断言都更常红。

![检查器当场抓住一次夸大](shots/s1_guards_against_inflation.png)

*把 README 里的"6 个三路完全一致"人为改回"全部三路完全一致"之后，检查立刻变红。**这是演示性破坏，跑完已还原**。*

## 11.1 而就在我写这篇文章的时候，它又发生了一次，而且没被抓到

那一条是关于装置自证的：我写"知情复核者把约 45 条自我批评无差别判为不过头"。这个"约 45 条"是我估的。

真实的条目数是 37。

我在一个以"不要夸大"为主题的项目里，把一个数字夸大了两成，而且它被写进了六处文档——README、论文附录、审读记录、自动生成的报告，还有这篇文章的初稿——没有一条检查发现它。

为什么没被发现？因为没有任何检查断言过这个数字。我的 275 项检查里有断言"没有一条被判过头"，但没有断言"这里一共有多少条"。检查器只能守住它被告知要守的东西，而我没想到要给这个数字设防，因为我根本没意识到我会在这里夸大。

发现它的方式很朴素：我要在文章里用这个数字，于是去数了一遍。

这就是我能给出的全部教训里最实在的一条：要写进文里的每一个数字，去数一遍，哪怕它看起来只是约数。

（写这一段的时候还发生了第二次。我在文章里引用了 `spec_code_field_check`，顺手给它配了一句 docstring，而那个函数根本没有 docstring。我在一篇讲"不要编造"的文章里编造了一段代码引用。已改。）

## 11.2 边界

那 275 项检查只保证一件事：没有未标注项。它们不保证标注是诚实的。诚实只能靠记录——把每一次推翻都写下来，包括那些推翻自己的。而记录这件事只在你**不打算把它藏起来**的时候才有意义。

# 十二、路碑

这一路上我以为我在做三件不同的事：先是设计一个架构，然后是测量它的性质，最后是验证我的想法新不新。

到最后我发现这三件事是同一个错穿着三件衣服：用我自己手里的、我自己控制的样本，去断言关于世界的性质。

设计时我把要证的性质写进了装置；测量时我把判据定成了自己够得着的那把尺子；验证时我把"搜不到"当成了"不存在"。

我能防住其中一部分。防不住的那部分——判据本身、盲区本身——只能靠外面的人。

所以我把它留在这里当一块路碑：它标出一个方向，也标出那条走不通的死路。如果你也在用 AI 做点什么东西，我希望这块碑能让你早一点停下来，先查一遍，再动手。

那样的话，我这个项目就不算全白做。
